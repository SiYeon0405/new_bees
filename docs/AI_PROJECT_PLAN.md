## 1 기획 결론

new_bees를 **소규모 개발팀의 문서와 변경 이력을 근거로 답하는 AI 협업 공간**으로 고도화한다. 핵심 가치는 팀원이 파일을 보관하는 데서 그치지 않고, 필요한 정책과 결정 사항을 빠르게 찾고 근거까지 확인하는 것이다.

첫 제품은 “팀 문서를 업로드하고 질문하면, 접근 가능한 최신 문서에서 찾은 근거와 함께 답을 받는다”는 하나의 흐름을 완성한다. 기존 Django·MySQL 구조를 유지하고, 문서 검색과 AI 처리만 필요한 만큼 추가한다. 이후 실제 사용 결과를 보고 버전 변경 요약, 신규 팀원 안내, GitHub 연결을 확장한다.

**우선 결정:** 기존 인증·그룹·파일 흐름 안정화를 AI 개발의 선행 조건으로 둔다. AI 기능을 추가하기 위해 Spring Boot로 재작성하거나, 별도 FastAPI 서버와 여러 에이전트를 동시에 도입하지 않는다. 이 선택은 기존 코드의 활용도를 높이고 장애 원인과 변경 범위를 줄이기 위한 것이다.

### 분석 범위와 해석

현재 로컬 저장소의 설정, URL, 모델, 마이그레이션, 직렬화기, 뷰, GitHub 연동 코드, 의존성, Docker 구성, 테스트 파일을 정적으로 검토했다. 이 문서에서 “확인”은 코드 확인을 뜻한다. DB 복원, 서버 기동, 실제 로그인, GitHub OAuth, 부하 테스트와 모델 품질 평가는 실행하지 않았으므로 운영 정상 동작을 확인한 것으로 해석하면 안 된다. 아래 수치와 일정은 개발 목표 및 추정치다.

## 2 사용자가 겪는 문제와 제품 방향

대상은 학교 팀 프로젝트, 동아리 개발팀, 3~10명 규모의 소규모 개발팀이다. 초기 검증은 실제 사용 의사가 있는 1~2개 팀으로 한정한다.

문서는 있지만 어느 파일이 최신인지 모르고, API 정책이나 지난 결정의 이유를 찾으려면 파일과 대화를 다시 읽어야 한다. 새 팀원은 같은 질문을 반복하고, 문서 수정자는 변경 내용을 별도로 설명해야 한다. new_bees는 이 탐색과 설명의 비용을 줄인다.

| 사용자 | 현재 불편 | 제공 가치 | 초기 검증 방법 |
|---|---|---|---|
| 팀원 | 필요한 정책이 있는 파일을 직접 찾음 | 질문으로 근거 문서와 관련 부분 확인 | 같은 과제를 기존 방식과 AI 방식으로 수행 |
| 팀장과 PM | 문서 변화와 결정 사항을 다시 정리 | 버전별 변경 요약 및 확인할 항목 초안 | 실제 diff와 요약을 대조 |
| 신규 팀원 | 업무 맥락을 파악하기 어려움 | 자료에 근거한 온보딩 질문·답변 | 담당자 도움 없이 답을 찾는 비율 측정 |

예시 질문은 “로그인 토큰 만료 정책은?”, “파일 업로드 크기 제한은?”, “API 명세서 v2에서 응답 필드가 어떻게 바뀌었나?”로 정한다. 문서에 결정 이유가 없으면 AI가 이유를 추측하지 않고, 확인 가능한 변경 사실만 답한다.

일반적인 AI 채팅과의 구분점은 **그룹 권한, 문서 버전, 근거 추적, 변경 이력**이다. 검색 결과의 출처를 누르면 실제 파일 버전과 해당 부분으로 이동할 수 있어야 한다.

## 3 현재 프로젝트 분석

### 3.1 DB 영향 분석

기존 MySQL을 업무 데이터의 기준 저장소로 유지한다. 현재 코드에는 `groups.Group`과 `group_create.Group`, `groups.GroupMember`와 `group_join.GroupMembership`이 공존한다. 파일도 `files.File/FileVersion`과 `workspace.UploadedFile`로 분리돼 있다. 서로 다른 그룹 체계에 AI 색인을 연결하면 접근 제어와 데이터 매핑이 복잡해진다.

**권장 기준 모델은 설치된 앱과 기존 관계를 우선해 `groups.Group/GroupMember`, `files.File/FileVersion`, `users.User`로 잡는다.** 다만 DB의 실제 사용량과 스키마를 확인하기 전까지 최종 통합 대상으로 확정하지 않는다. 빈 DB라면 기준 모델에 맞춰 정리하고, 기존 데이터가 있다면 백업과 매핑 검증 후 이관한다. 초기부터 테이블 삭제나 전체 마이그레이션 재생성을 하지 않는다.

### 3.2 API 영향 분석

현재 `config/urls.py`는 관리자·JWT·사용자 경로를 연결한다. 그룹·파일·검색·알림·GitHub 기능은 코드가 있어도 이 URL 구성에서는 외부에서 사용할 수 없다. 기능 파일의 존재와 실제 제공 API를 구분해야 한다.

로그인·회원가입 등 기존 경로는 가급적 유지한다. 로그인 응답은 잘못된 `username` 참조를 `nickname`으로 정리하고 응답 계약을 문서화한다. 그룹·파일·AI API는 그룹 ID가 명시되는 경로로 추가한다. 사용자의 권한은 요청의 user_id나 모델 응답이 아닌 서버의 인증 정보와 DB 멤버십으로 판단한다.

### 3.3 계층별 구조

| 검토 순서 | 현재 상태 | 최소 변경 방향 |
|---|---|---|
| Entity에 해당하는 Model | User·Group·FileVersion 등 기반 모델 존재, 별도 구현 중복 | 기준 모델 선정 후 관계와 제약조건 보강 |
| Repository에 해당하는 ORM 조회 | 뷰 안에 직접 조회가 집중 | 그룹 제한 조회를 selectors.py 등 한곳으로 모음 |
| Service | GitHub 함수와 뷰에 업무 로직 혼재 | 업로드·권한·버전·AI 처리 단위의 함수형 서비스 추출 |
| Controller에 해당하는 View | 인증 API는 연결, 다른 기능은 연결 누락 | 검증·권한·서비스 호출·응답 변환 역할로 제한 |
| Test | 확인한 tests.py는 기본 템플릿 수준 | 로그인 회귀, 그룹 격리, 파일 처리, AI 평가 순으로 추가 |

Django에서 Java식 Repository 클래스를 모든 모델마다 만들 필요는 없다. 여러 뷰에서 반복하는 권한 조건과 조회만 공통화한다.

### 3.4 코드에서 확인한 우선 문제

P0는 AI 구현 전 해결, P1은 파일 기능 출시 전 해결, P2는 운영 공개 전 정리 대상으로 분류한다. 현재 미연결 코드의 문제는 해당 기능을 연결할 때 활성화되는 위험이다.

| 우선 | 확인 사항과 근거 파일 | 영향 | 해결 및 검증 |
|---|---|---|---|
| P0 | users/serializers.py에 같은 이름의 EmailTokenObtainPairSerializer가 두 번 정의되고 마지막 정의가 user.username 참조 | User에 username이 없어 정상 인증 후 응답 구성 실패 가능 | 하나로 정리하고 올바른 계정 로그인 응답 검증 |
| P0 | config/urls.py에 사용자 외 기능 연결 누락 | 그룹·파일·AI의 기반 경로가 제공되지 않음 | URL과 설치 앱을 기준 모델 중심으로 정리하고 경로 테스트 |
| P0 | groups와 group_create에 서로 다른 Group 존재 | 멤버십·파일·검색 권한 기준 불일치 | 데이터 조사 후 기준 그룹과 매핑 확정 |

| P0 | settings.py에 비밀키·DB 비밀번호 고정, DEBUG=True | 공개 배포 시 설정·정보 노출 위험 | 환경변수·별도 운영 설정·노출 이력이 있는 실제 키 교체 |

| P1 | 일반 업로드의 filename, filepath 대입문에 끝 쉼표 존재 | 문자열 대신 튜플 전달로 잘못된 경로 저장·조회 가능 | 문자열 처리와 파일명·크기·경로 검증 |
| P1 | GitHub 업로드에서 decode 실패 후 uploaded_file.read() 재호출 | 이미 읽은 스트림에서 빈 데이터 처리 및 이중 인코딩 가능 | 바이트를 한 번 읽고 GitHub 경계에서 한 번만 base64 인코딩 |
| P1 | invite_code/views.py가 요청 user_id를 사용하고 group.creator 및 user.username 참조 | 타인 가입 조작 가능성, 존재하지 않는 필드 오류 | request.user 사용, 그룹 owner와 nickname 사용, 만료·권한 검사 |
| P1 | workspace/git_service.py가 정의되지 않은 GitVersion·GitActionLog와 git_tracked 사용 | 해당 모듈 활성화 시 import·필드 오류 | MVP에서 연결 제외, 사용 경로 확인 후 실제 모델에 맞게 수정 |
| P1 | 같은 서비스에 서버 소스 경로를 대상으로 한 git push·force push·checkout 구현 | 실행 시 서비스 코드 이력·동시 요청 충돌 위험 | 문서 저장과 서비스 소스 Git 분리, 후속 단계에서 GitHub API 기반 읽기부터 복구 |
| P1 | workspace 화면에서 참조하는 upload_and_list.html이 저장소에 없음 | 해당 화면 호출 시 템플릿 오류 가능 | 새 최소 UI를 구현하거나 템플릿 추가 |
| P1 | search_filter가 Document.objects.all() 및 author__username 사용 | 연결 시 그룹 격리 누락과 검색 필드 오류 | 기준 파일·버전과 사용자 모델에 맞춘 제한 조회 |
| P2 | 루트·backend requirements가 다르고 requests·social_django 등 사용 코드와 의존성 목록 불일치 | 기능 활성화 후 모듈 오류, 환경 재현성 저하 | 실제 사용하는 의존성만 한곳에서 고정하고 설치 검증 |
| P2 | 확인한 테스트 파일이 기본 템플릿, 마이그레이션은 생성 Django 버전과 설치 범위 차이 존재 | 회귀·재현성 검증 부족 | 지원 버전과 의존성을 확정하고 빈 DB 설치·기존 DB 업그레이드 검증 |

현재 root requirements는 Django 4.2 이상 5.0 미만 범위이고 일부 마이그레이션 생성 주석에는 Django 5.2가 보인다. 생성 주석 차이만으로 마이그레이션 실패를 단정하지 않고 실제 호환성을 검증한다. 신규 운영 환경은 지원 중인 Django 버전과 Python·DRF·JWT·MySQL 드라이버 조합을 확인해 확정한다.

Docker Compose는 개발 서버 실행 구성이다. 운영에서는 별도 WSGI/ASGI 서버·TLS·로그·백업을 구성한다. 현재 Dockerfile은 루트 requirements를 설치하고 전체 저장소를 복사하지만 Compose의 backend 볼륨 마운트에 기대는 구조이므로, 볼륨 없는 이미지 실행도 별도로 검증한다.

## 4 목표 기능과 범위

### 4.1 첫 출시 범위

| 기능 | 사용자 동작 | 필수 결과 | 제외 범위 |
|---|---|---|---|
| 그룹과 멤버 관리 | 그룹 생성·초대·가입 | 소유자·멤버 구분, 접근 가능한 그룹만 조회 | 조직 계층·복잡한 역할 체계 |
| 문서와 버전 관리 | TXT·Markdown 업로드, 새 버전 등록 | 버전 불변성, 처리 상태·실패 사유·재시도 | OCR·동영상·ZIP·임의 코드 실행 |
| 출처 기반 질문·답변 | 그룹 선택 후 질문 | 답변·파일명·버전·인용 부분·원문 링크 | 외부 웹 검색·전체 GitHub 코드 분석 |
| 검색 및 피드백 | 근거 클릭·답변 평가 | 근거 확인과 잘못된 답변 신고 | 자동 학습·개인화 추천 |
| 최소 제품 화면 | 로그인·그룹·문서·질문 화면 | 처음부터 끝까지 사용할 수 있는 웹 흐름 | 별도 모바일 앱·실시간 채팅 |

현재 저장소에는 완성된 프런트엔드가 없다. 초기에는 Django 템플릿과 필요한 JavaScript로 최소 화면을 만든다. React/Next.js를 추가하면 UI 개발 경험을 얻을 수 있지만 인증·CORS·별도 배포 범위도 늘어난다. 첫 검증 이후 실제 필요가 있을 때 분리한다.

텍스트 PDF는 첫 흐름이 안정된 뒤 추가한다. 파서·페이지 인용·표 추출 검증이 필요하며 스캔 PDF는 OCR을 도입하기 전에는 명확히 지원하지 않는다고 안내한다.

### 4.2 후속 기능

**문서 버전 변경 요약:** 버전 A와 B를 서버가 직접 읽어 diff를 계산하고 AI가 변경 사실·확인할 항목을 설명한다. 실제로 다른 부분만 전달해 비용과 추측을 줄인다. 코드 영향 분석은 관련 코드와 테스트까지 조회하는 별도 기능이므로 첫 버전에서는 “확인 권장 항목”으로 표시한다.

**팀 활동 정리:** 선택한 기간의 문서 변경과 이후 연결될 댓글에서 결정 사항·미해결 질문·할 일 초안을 추출한다. 담당자·마감일은 근거가 없으면 비워 두며, 사용자가 검토하기 전에는 실제 할 일로 등록하지 않는다.

**온보딩 안내:** 최신 문서에 근거한 시작 순서와 확인할 자료를 제공한다. 별도 에이전트를 추가하기보다 같은 검색·인용 기반을 재사용한다.

**GitHub 연결:** 처음에는 사용자가 선택한 저장소의 문서와 커밋을 읽기 전용으로 연결한다. 이슈 생성은 사용자가 제목·내용·대상 저장소를 확인하고 실행할 때만 허용한다. 서비스 소스 저장소와 팀 문서 연동 저장소는 별도 데이터로 관리한다.

### 4.3 사용자 시나리오와 화면

1. 팀장이 그룹을 만들고 팀원을 초대한다.
2. 문서 목록에서 Markdown 명세서를 업로드한다. “처리 중” 상태를 표시하고 완료되면 “질문 가능”으로 바뀐다.
3. 팀원이 “파일 크기 제한은?”을 질문한다.
4. AI 답변 아래에 “파일 정책 v3 / 업로드 제한 / 문단 4” 출처가 표시된다.
5. 출처를 누르면 권한 확인 후 해당 버전과 문단을 보여준다.
6. 문서에 답이 없으면 “현재 팀 문서에서 확인할 수 없습니다”와 찾은 관련 자료를 표시한다.
7. 문서가 삭제되거나 사용자가 그룹에서 나가면 검색·답변 기록·원문 접근에서도 즉시 권한을 다시 적용한다.

핵심 화면은 그룹 목록, 그룹 내 문서 목록과 버전, 업로드 처리 상태, 질문·답변, 근거 원문 보기다. AI 모델명이나 임베딩 설정은 일반 사용자 화면에 노출하지 않고 관리 설정으로 둔다.

## 5 AI 기술 연결 설계

### 5.1 기술 선택

| 기술 | 역할 | 도입 시점 | 선택 이유와 트레이드오프 |
|---|---|---|---|
| 외부 LLM API | 검색된 근거에 기반한 답변과 요약 | 첫 AI 기능 | 직접 모델 운영보다 시작이 빠르지만 비용·외부 전송 정책 확인 필요 |
| 다국어 임베딩 | 한국어 문서와 질문의 의미를 검색 가능한 벡터로 변환 | 첫 AI 기능 | 한국어·영문 기술 용어 혼합 질문으로 후보 품질 비교 |
| RAG | 찾은 문서 조각을 답변의 근거로 제공 | 첫 AI 기능 | 재학습 없이 문서를 반영하지만 검색과 인용 품질 관리 필요 |
| Qdrant | 그룹·버전 필터를 가진 벡터 색인 | 첫 AI 기능 | MySQL을 유지할 수 있지만 별도 저장소 운영·동기화 필요 |
| Celery와 Redis | 문서 분석·색인·재시도 처리 | 문서 비동기 처리 | 웹 응답 지연을 줄이지만 워커·브로커 관찰 필요 |
| 구조화된 출력 | 답변·근거 ID·확인 불가 상태를 고정 형식으로 수신 | 첫 AI 기능 | 파싱은 안정화하지만 사실 정확성을 보장하지 않음 |
| 키워드와 의미 검색 결합 | API 경로·에러코드 등 정확 일치 보완 | 검색 평가에서 필요 확인 후 | 검색 경로와 평가 비용 증가 |
| Reranker | 검색 후보 중 질문과 더 관련된 조각 우선 배치 | 기본 검색의 한계 확인 후 | 정확도 개선 가능, 추론 비용과 지연 추가 |
| 도구 호출과 MCP | 외부 시스템을 조회하거나 작업 수행 | 후속 검토 | 연동 수요가 생기면 도입, 초기 RAG에는 필수 아님 |

LLM과 임베딩은 서로 별도로 선택한다. 첫 비교는 같은 평가셋으로 API 제공자 2곳 이내에서 진행하고 정답률·근거 일치·p95 지연·질문당 비용으로 결정한다. 이름에 “최신”이 붙은 모델을 무조건 선택하지 않는다. SDK 직접 호출과 작은 Provider 인터페이스로 시작하고, 여러 검색 파이프라인이 복잡해질 때 LangChain 같은 도구의 도입 비용을 다시 판단한다.

Qdrant payload 필터는 검색 범위를 좁히는 수단이다. 사용자 인증과 멤버십 검증은 Django가 담당해야 하며, 필터만으로 전체 권한 체계가 완성되는 것은 아니다. [기술 자료 T2]

### 5.2 전체 구조

~~~mermaid
flowchart TD
    UI["웹 화면"] --> API["Django API와 권한 검사"]
    API --> DB["MySQL 업무 데이터"]
    API --> STORE["문서 파일 저장소"]
    API --> QUEUE["작업 큐"]
    QUEUE --> WORKER["문서 분석 워커"]
    WORKER --> STORE
    WORKER --> EMB["임베딩 API"]
    WORKER --> VECTOR["Qdrant 검색 색인"]
    API --> RETRIEVE["권한을 적용한 검색"]
    RETRIEVE --> VECTOR
    RETRIEVE --> DB
    RETRIEVE --> LLM["LLM 답변 생성"]
    LLM --> API
~~~

Django를 인증·업무 데이터·권한의 중심으로 유지한다. 워커와 검색 서비스는 별도 배포할 수 있지만 같은 Django 코드베이스의 모듈로 시작한다. 로컬은 Docker Compose로 API·MySQL·Redis·워커·Qdrant를 구성하고 운영 공개 시 각 서비스의 네트워크와 자격 증명을 분리한다.

### 5.3 문서 수집 흐름

1. API가 그룹 멤버십과 업로드 권한, 확장자·MIME·바이트 크기·인코딩을 검사한다. 첫 제한안은 텍스트 파일 5MB이며 파일 수·총 저장량도 별도로 제한한다.
2. 원본을 저장하고 FileVersion 및 AI 작업을 DB 트랜잭션으로 기록한다. DB 커밋 후 색인 작업을 발행한다. `transaction.on_commit()`을 사용할 수 있으나 브로커 발행까지 원자적으로 보장하지는 않는다. [기술 자료 T1]
3. 발행 실패나 워커 중단에 대비해 대기 중 작업을 다시 찾는 복구 작업을 둔다. 운영 신뢰성이 필요해지면 outbox 패턴으로 강화한다.
4. 워커가 텍스트를 추출하고 제목·문단 구조에 따라 나눈다. 초기 실험값은 조각당 약 500토큰, 중복 약 80토큰이며 문서 특성에 따라 조정한다.
5. 조각별 원문 위치와 버전·해시를 저장하고 임베딩을 생성한다. API 토큰 한도 초과와 긴 한 문단도 처리한다.
6. 색인 완료 후에만 해당 버전을 검색 가능 상태로 전환한다. 중간 생성된 조각은 검색에서 제외한다.
7. 동일한 버전·내용 해시·임베딩 모델·분할 규칙이면 기존 작업을 재사용한다. 실패 작업만 제한 횟수 재시도한다.

DB와 파일 저장소, 벡터 저장소는 하나의 트랜잭션으로 묶이지 않는다. 원본 저장 성공 후 DB 실패로 남은 파일은 정리하고, DB 삭제 후 외부 삭제 실패는 재시도 작업으로 복구한다.

### 5.4 질문 처리 흐름

1. 사용자 인증 후 그룹 멤버십을 확인한다. 기본 검색 대상은 그룹의 최신 공개 문서 버전이다.
2. 서버가 DB에서 읽을 수 있는 문서 버전을 구하고 검색 필터를 구성한다. 클라이언트가 허용 문서 ID를 정하도록 두지 않는다.
3. 임베딩 검색 후보 8~12개부터 실험한다. 그룹·현재 버전·활성 상태 필터를 적용하고 필요하면 검색 후 DB 권한도 재검증한다.
4. 문맥 한도에 맞게 4~6개 근거를 선택한다. 검색 점수 임계값은 모델별로 평가해 정하고 보편적인 정답 기준으로 취급하지 않는다.
5. 모델에는 질문·근거 조각·조각 ID·답변 규칙만 전달한다. 저장소 전체나 사용자 토큰은 전달하지 않는다.
6. 모델은 answer, citations, answer_status를 반환한다. 출처는 전달된 chunk_id만 허용한다.
7. 서버가 출처 ID·버전·실제 인용 문자열을 검증한다. 검증 실패 시 제한된 재시도 또는 “근거 확인 실패”로 응답한다.
8. 응답 직전 그룹 권한·삭제 여부·최신 버전 정책을 다시 확인한다. 사용량과 지연을 기록하고 평가 버튼을 제공한다.

답변에는 “문서에 명시된 사실”과 “추가 확인이 필요한 제안”을 구분한다. 근거가 없으면 대답하지 않는 기능도 성공 동작으로 정의한다. 출처 ID가 유효하다는 검사만으로 답변의 사실성이 보장되지는 않으므로 별도의 근거 충실도 평가가 필요하다.

네이티브 citations와 JSON 구조화 출력의 동시 지원은 제공자별로 다르다. 예를 들어 검토한 Claude 문서는 두 기능의 호환 제약을 안내한다. MVP에서는 애플리케이션이 chunk_id를 관리하고 구조화 응답을 검증해 종속성을 줄인다. [기술 자료 T3]

## 6 DB 변경 계획

### 6.1 기존 모델 정리

- Group의 소유자와 GroupMember의 역할을 권한 기준으로 유지한다. 그룹 생성 시 소유자의 멤버십도 함께 생성하고 중복을 막는다.
- File은 그룹에 속하고 FileVersion은 원본과 내용 해시를 보유한다. 버전은 덮어쓰지 않고 새 레코드로 생성한다.
- File에 현재 공개 버전 참조, 삭제 상태를 추가하고 FileVersion에는 업로더·크기·MIME·해시를 추가한다. 그룹 ID는 클라이언트 입력을 그대로 신뢰하지 않는다.
- 버전 번호는 파일 내 유일해야 하며 동시 업로드 시 DB 잠금·유일 제약·재시도를 이용해 충돌을 처리한다.
- 기존 UploadedFile의 그룹을 추정할 수 없는 데이터는 임의 배정하지 않고 별도 검토 대상으로 둔다.

### 6.2 새 데이터 구조

| 구조 | 주요 필드 | 관계와 제약 | 목적 |
|---|---|---|---|
| AIProcessingJob | kind, file_version_id 또는 question_id, status, attempts, error_code, index_revision, queued_at, completed_at | 작업 종류에 따라 대상 FK 하나만 지정, 버전·처리 종류·세대 중복 제어 | 문서·질문 처리 상태와 재시도 |
| DocumentChunk | file_version_id, ordinal, content, locator, content_hash, embedding_model, index_revision, point_id | 버전·세대·순번 유일, 버전 FK | 근거 위치·재색인 추적 |
| AIQuestion | group_id, asked_by, question, answer, status, model, prompt_version, latency_ms, input_tokens, output_tokens | 그룹·질문자 FK, 보존기간 적용 | 답변 이력·비용·품질 |
| AICitation | question_id, chunk_id, quoted_text | 질문 FK, 삭제 정책 명시 | 답변과 실제 근거 연결 |
| AIFeedback | question_id, user_id, rating, reason | 질문·사용자당 평가 갱신 | 오류 유형과 개선 |
| Group 확장 | ai_enabled, quota 설정 | 관리자만 수정 | 비용·기능 통제 |

텍스트 원문과 인용은 민감정보를 포함할 수 있다. 그룹·문서 삭제 시 청크·인용·답변 보존 정책을 함께 적용한다. 탈퇴한 사용자의 개인 AI 기록은 정책에 따라 익명화 또는 삭제하고, 다른 팀원의 공용 문서를 사용자 삭제의 부수 효과로 지우지 않도록 FK 정책을 검토한다.

Qdrant에는 group_id, file_id, file_version_id, chunk_id, index_revision과 임베딩 모델 정보를 보관한다. 진실의 기준은 MySQL이며 벡터 데이터는 재생성 가능한 색인으로 취급한다. 필터에 사용하는 필드에는 payload index를 설계한다. [기술 자료 T2]

### 6.3 이관과 복구

개발 DB가 비어 있는지 먼저 확인한다. 데이터가 있다면 원본 DB와 파일을 함께 백업하고, 기존 ID와 기준 ID의 매핑을 생성한다. 새 FK는 임시 nullable로 추가한 뒤 이관·건수·고아 레코드 검증 후 NOT NULL과 유일 제약을 적용한다. 되돌릴 수 있는 기간 동안 기존 테이블을 유지한다. 파일 이름이 같다는 이유만으로 같은 문서로 합치지 않는다.

임베딩 모델을 바꿀 때는 기존 색인에 다른 차원의 벡터를 섞지 않는다. 새 세대로 재색인하고 평가 후 전환하며, 실패하면 기존 색인으로 되돌린다.

기존 인증·사용자 API 경로는 유지한다. 아래는 구현할 계약의 초안이며 현재 동작하는 API 목록이 아니다.

| POST /api/groups/{id}/invites/ | 만료되는 초대 생성 | 201 code, expires_at | 그룹 소유자 |
| POST /api/groups/join/ | 초대 코드로 가입 | 201 membership 또는 기존 가입 상태 | request.user 본인 |

| DELETE /api/groups/{id}/files/{file_id}/ | 논리 삭제와 정리 예약 | 202 | 업로더 또는 그룹 소유자 |
| POST /api/groups/{id}/files/{file_id}/diff-summary/ | 후속 기능 A·B 버전 요약 | 202 job_id | 그룹 멤버 |

초기 질문 처리는 비동기 202와 폴링으로 통일한다. UI는 1~2초 간격에서 시작해 간격을 늘리고 완료·실패 시 중단한다. 후속 단계에서 SSE로 전환할 수 있다. 폴링 요청도 권한과 호출 제한을 적용한다.

문서 처리 상태는 QUEUED → PROCESSING → READY 또는 FAILED로 관리하고, 삭제 요청 시 DELETING → DELETED로 전환한다. 질문 상태는 QUEUED → GENERATING → COMPLETED 또는 FAILED이며, “근거 없음”은 실패가 아닌 COMPLETED와 answer_status=insufficient_evidence로 반환한다.

401은 인증 실패, 접근 불가능한 리소스는 일관된 404 정책, 413은 파일 크기 초과, 415는 미지원 형식, 429는 사용량·요청 제한으로 정한다. 파일별 버전 불일치와 중복 업로드 정책은 409로 구분한다. 제공자 장애 세부 내용과 비밀키는 API 응답에 노출하지 않는다.

외부 LLM 호출은 재시도 시 중복 과금 가능성이 있으므로 작업 상태와 시도 번호를 기록한다. 모델에서 받은 내용은 안전한 텍스트나 제한된 Markdown으로 렌더링하고 HTML은 실행하지 않는다.

## 8 보안과 운영 설계

### 그룹 격리

그룹 ID를 아는 것만으로 문서·원본·질문·근거·처리 상태에 접근할 수 없어야 한다. 모든 조회는 현재 멤버십을 적용하고 사용자의 그룹 탈퇴를 즉시 반영한다. 질문과 답변 기록은 첫 출시에서 질문자 개인에게만 보여주고 팀 공유는 후속 권한 정책으로 추가한다.

검색 전 필터, 검색 후 DB 검증, 응답 직전 검증을 적용한다. 캐시는 그룹·문서 버전 집합·권한 상태를 포함하고 초기에는 질문 응답 캐시를 생략해 누출 경로를 줄인다. 다른 그룹이 같은 파일 해시를 올렸더라도 원문과 답변을 공유하지 않는다.

### 문서 삭제와 최신성

삭제 요청 시 DB에서 즉시 검색 불가로 만들고 원문·청크·벡터·인용·캐시 정리를 예약한다. 벡터 삭제가 늦어져도 검색 후 DB 검증에서 제외한다. 처리 중이던 워커도 완료 직전 삭제 상태를 검사해 삭제 자료를 재등록하지 않는다.

새 버전 처리 중에는 기존 공개 버전을 사용하되 화면에 새 버전 처리 중임을 알린다. 새 색인이 완전히 준비된 뒤 현재 공개 버전을 원자적으로 전환한다. 사용자가 명시적으로 과거 버전을 선택한 경우에만 과거 문서를 답변 근거로 사용한다.

### 프롬프트 주입과 외부 전송

문서 속 “이전 지시를 무시하라”, “다른 팀 자료를 보여 달라” 같은 문장은 명령이 아닌 데이터로 취급한다. 프롬프트 규칙만 믿지 않고 모델에 다른 그룹 자료와 실행 도구를 주지 않는다. 첫 출시에는 웹 접근·셸 실행·저장소 쓰기 도구를 연결하지 않는다.

API 키와 GitHub 토큰은 서버에서 관리하고 브라우저나 프롬프트에 전달하지 않는다. AI에 전송할 데이터 범위와 보존 정책을 안내하고 운영용 계약·지역·제공자 데이터 정책을 확인한다. 공개 데모는 가상 팀 문서를 사용한다. 보안키·실사용 비밀번호가 자료에 들어가지 않도록 업로드 경고와 탐지를 마련하되 탐지만으로 완전 차단을 보장하지 않는다.

### 파일과 GitHub 안전성

서버 저장 파일명은 내부 ID로 생성하고 사용자가 준 경로를 직접 파일 시스템 경로로 쓰지 않는다. 원본 다운로드는 권한을 거치는 경로만 사용한다. 파서는 크기·시간·메모리를 제한하고 파일을 실행하지 않는다.

서비스 코드의 origin과 사용자 문서의 GitHub 연결을 분리한다. 원래 SiYeon0405/bees 저장소에는 쓰지 않는다. 개발 소스 변경을 올리는 대상은 new_bees뿐이며, 앱의 문서 연동은 사용자가 별도로 선택한 저장소만 사용한다. force push와 서버 소스 checkout 기능은 AI 및 일반 사용자 API에 연결하지 않는다.

### 장애와 관측

AI 장애가 문서 조회·다운로드를 막지 않도록 분리한다. timeout, 제한된 지수 백오프, 최대 시도, 일일 사용량 상한과 동시 실행 수를 둔다. Redis 큐 길이·가장 오래 대기한 작업·색인 실패율·LLM 오류율·p95 지연·토큰 사용량을 관찰한다.

로그에는 원문·비밀키·질문 전체를 기본 기록하지 않고 request_id·group_id·작업 ID·오류 유형·시간·토큰 수를 기록한다. DB·원본 파일은 백업하고 복원 연습을 한다. 벡터 색인은 DB와 원본에서 재생성하는 절차도 문서화한다.

## 9 개발 순서와 예상 일정

**총 120~160시간, 주 15시간 투입 시 약 8~11주**를 초기 추정으로 둔다. 기존 데이터 복잡도, 인프라 학습, PDF·UI 범위에 따라 늘어날 수 있다. 날짜보다 단계별 완료 조건을 우선한다.

| 단계 | 예상 시간 | 주요 작업 | 완료 조건 |
|---|---|---|---|
| 0 재현과 기준 확정 | 12~16h | 설치·DB 조사·앱과 URL·사용자 필드 정리 | 빈 DB에서 기동, 회원가입·로그인·내 정보 조회 성공 |
| 1 그룹과 파일 기반 | 24~30h | 기준 그룹, 초대, 권한, 업로드·버전·다운로드 | 두 그룹 간 접근 차단과 새 버전 보존 테스트 통과 |

후속 문서 변경 요약은 첫 출시 후 별도 15~25시간으로 추정하고, GitHub 연동은 OAuth·권한 설계 범위를 확인한 뒤 다시 산정한다. 첫 일정에는 두 기능을 포함하지 않는다.

### 최소 파일 변경 원칙

우선 users/serializers.py, config/settings.py, config/urls.py, 실제 사용하는 requirements와 Docker 구성에서 기동 문제를 해결한다. 다음으로 groups와 files 앱에 기준 모델·API·권한·서비스를 추가한다. 중복 앱은 한 번에 삭제하지 않고 호출을 차단하거나 검증된 로직만 옮긴다.

AI 구현은 backend/ai_assistant/ 아래 models.py, serializers.py, views.py, urls.py, services.py, retrieval.py, providers.py, tasks.py와 의미 있는 tests로 시작한다. 파일의 양보다 책임 경계를 우선하며, 작은 기능마다 클래스를 만드는 구조는 피한다. API 서버를 분리하지 않고 같은 Django 프로젝트에서 시작한다.

브랜치는 기반 복구, 파일 기능, AI 색인, 질문 응답처럼 검토 가능한 단위로 나누고 각 단계의 DB 변경과 API 계약을 함께 리뷰한다. 이 기획서 작성 과정에서는 애플리케이션 코드를 수정하거나 추가 커밋·푸시하지 않는다.

### 10.2 AI 평가셋

가상 문서 약 20개에서 사람이 정답과 근거 버전을 작성한 60문항을 만든다. 정답 가능 30개, 문서에 없는 질문 10개, 버전·동명이의 문서 혼동 10개, 권한·악성 지시 10개로 구성한다. 그룹 격리는 별도의 자동화된 보안 테스트로도 검증한다.

튜닝용과 최종 검증용을 분리하고 모델·프롬프트·분할 규칙·검색 설정 변경 전후에 같은 검증셋으로 비교한다. 자동 LLM 평가는 보조로 사용하고 인용 충실도와 중요 정책 답변은 사람이 확인한다.

| 지표 | 초기 목표 | 계산과 해석 |
|---|---|---|
| Retrieval Recall@5 | 정답 가능 질문의 85% 이상 | 상위 5개에 정답 근거가 최소 1개 있는 질문 비율 |
| 근거 충실도 | 검토한 사실 주장 90% 이상 | 답변 주장 중 실제 인용 내용으로 뒷받침되는 비율 |
| 답변 유보 정확도 | 답이 없는 질문의 90% 이상 | 근거 없는 확답을 하지 않는 비율 |
| 잘못된 그룹 노출 | 평가·보안 테스트에서 0건 | 발견 시 출시 차단, 절대 안전 보장이라는 의미는 아님 |
| 응답 지연 | p95 15초 이하 | 소규모 동시 질문 3개, 작업 접수부터 완료까지 측정 |
| 문서 처리 성공률 | 지원 형식 정상 파일의 95% 이상 | 거절 대상 파일은 분모에서 별도 분리 |
| 정보 탐색 시간 | 기존 방식 대비 중앙값 30% 단축 | 같은 사용자가 난이도 비슷한 과제를 번갈아 수행 |

목표를 달성하기 전에 수치를 성과로 홍보하지 않는다. 한국어 기술 문서에서 검색이 부족하면 먼저 분할 규칙·문서 제목·정확 키워드를 점검하고, 이후 하이브리드 검색과 reranker를 순서대로 비교한다.

## 11 비용과 범위 관리

API 단가를 임의로 고정하지 않는다. 구현 시점의 제공자 공식 가격과 과금 단위를 확인하고 원화 환산 기준도 기록한다.

- 월 LLM 비용 = 질문 수 × 평균 입력 토큰 × 입력 단가 + 질문 수 × 평균 출력 토큰 × 출력 단가
- 색인 비용 = 신규·변경 문서 토큰 × 임베딩 단가 + 재시도·재색인 비용
- 운영 비용 = API·워커·MySQL·Redis·Qdrant·원본 저장소·백업·전송 비용
- 총비용에는 실패 호출·평가 호출·버전 변경 요약·중복 요청도 포함한다.

첫 파일럿 사용량 가정은 2개 팀, 팀당 문서 50개 이내, 팀당 하루 질문 20개 이내다. 문서 길이와 질문 토큰은 실제 측정 전까지 확정하지 않는다. API 예산은 월 3만원을 내부 상한의 출발안으로 두되 **예상 청구액이 아닌 운영 한도**로 취급하고, 호스팅 비용은 별도 승인한다.

모델 출력 토큰과 근거 길이를 제한하고 그룹별 요청 한도·일일 예상 비용 예약을 둔다. 동시 요청으로 한도를 넘지 않도록 서버에서 원자적으로 사용량을 확보한다. 예산 부족 시 문서 검색은 유지하고 AI 생성만 제한한다. 같은 문서의 불필요한 재임베딩을 줄이고 전체 재색인은 관리자 작업으로 둔다.

### 학습용과 실제 운영의 차이

학습·로컬 검증은 합성 자료, 단일 머신 Compose, 제한된 호출량으로 충분하다. 실제 사용자를 받을 때는 운영 설정·TLS·키 교체·파일과 DB 백업·권한 테스트·삭제 정책·오류 관찰·제공자 데이터 처리 정책 확인이 선행돼야 한다. 외부 LLM의 답변 품질만 높이는 것으로 서비스 운영 준비가 끝나지는 않는다.

첫 출시에서 제외하는 항목은 모델 파인튜닝, 자동 코드 수정과 PR 병합, 전체 저장소 무제한 수집, 다중 에이전트, OCR, 음성, 모바일 앱이다. 문서 기반 질문의 품질과 실제 팀 사용이 확인된 뒤 하나씩 검토한다.

## 12 출시 판단과 다음 작업

첫 출시의 완료 조건은 다음과 같다.

- 새 환경에서 설치·DB 마이그레이션·서버 실행을 재현할 수 있다.
- 화면으로 가입·그룹 생성·초대·파일 업로드·질문·출처 확인을 수행할 수 있다.
- 문서·질문·원문·색인·작업 상태까지 그룹 격리 테스트가 통과한다.
- 문서 변경·삭제·탈퇴 후 오래된 권한과 근거가 노출되지 않는다.
- 실패한 작업이 사용자에게 설명되고 운영자가 원인과 재시도를 추적할 수 있다.
- 평가셋 결과·응답 시간·질문당 비용을 README 또는 별도 평가 문서로 남긴다.
- AI 제공자 장애 시 기본 파일 기능을 사용할 수 있다.

**바로 시작할 작업은 AI API 키 연결이 아니라 기반 복구다.** 로그인 직렬화기 중복과 사용자 필드 참조를 고친 뒤, 기준 그룹·파일 모델을 확정하고 테스트를 추가한다. 이 단계가 끝나면 작은 Markdown 문서 몇 개로 검색·근거 인용의 수직 흐름을 구현한다.

포트폴리오에는 “문서 질문 챗봇 구현”과 함께 그룹 격리 방식, DB와 벡터 색인의 일관성, 삭제 경합 처리, 검색 품질 변화, 실제 비용을 설명한다. 면접에서 설계 선택과 측정 결과를 근거로 말할 수 있는 프로젝트를 목표로 한다.
